# Shared face-trim transaction for door and window trims

Baseline review 2026-10-21 (componentization + abstraction lenses).

block/door/trim/DoorTrimActions.java:39-115 and block/window/trim/WindowTrimActions.java:41-132 implement the same fit / remove / announce flow: client shortcut, occupied-face no-op, read stack look, trims().with, shrink unless instabuild, give-back or drop, hurtAndBreak shears, sound + GameEvent. announce() is verbatim in both. Only the editable-host lookup and the window trimmed reconcile differ. Also DoorTrimItem:44 / WindowTrimItem:37 duplicate the registry accessor and the two remove() paths resolve the item differently.

Why: a change to trim economics must be made twice and drifts.
Direction: an attachment-level service in block/attachment/ (e.g. TrimFitting) taking a thin host strategy (editable-host lookup, setTrims, optional after-store hook); the trim item comes from the host.
